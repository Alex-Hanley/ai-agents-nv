So far our model can talk. It can't do anything. This video changes that,
and it's the heart of the module.

A tool is just a function. A tool call is just the model asking your code to
run that function. We're going to see what that looks like in the UI, then
build it by hand in Python, then measure whether what we built is fast enough
and cheap enough to use. That's notebooks 2 and 3, in one video.

[0:50] THE SEQUENCE
[SCREEN: deck 04, slide 2 (five steps)]

Here's the whole mechanism, five steps.

One: the model generates a JSON string naming a function and its arguments.
Two: your code parses and validates that string. Three: your code runs the
function. Four: the result is added back into the conversation as a message.
Five: the model uses the result to write its answer.

Notice which steps belong to whom. The model owns steps one and five.
Generating text. That's all it ever does. Your code owns everything in the
middle, including the actual execution. The model never runs code. It
produces a request, and your program decides whether and how to act on it.
Hold onto that, it's the safety foundation for every agent in this course.

[2:00] HOW THE MODEL SEES A TOOL
[SCREEN: deck 04, slide 3 (how the model sees a tool)]

Before the demo, it's worth killing the magic completely, because from the
model's side nothing special is happening.

The tool's description, its name, what it does, what parameters it takes, is
placed into the model's context as text. The model knows about your tool the
same way it knows anything else you tell it.

The description is written as a JSON schema because that's the format these
models were trained on. It's the shape of tool they're comfortable reading
and answering with.

And the tool call itself is ordinary generated text. A string that happens to
contain JSON. Which means it can come out malformed, and later in the course
we'll meet methods that guarantee valid JSON. In notebook 2 we deliberately
build the naive version first, so the mechanics stay visible.

[4:30] BUILDING THE LOOP
[SCREEN: screencast, notebook 2, the calculate function cell]

Here's the honest motivation for our first real tool. When you ask a language
model to multiply two large numbers, it doesn't compute. It produces
something that looks like an answer, from patterns in its training. For real
arithmetic we want a calculator, so the model's answers are grounded in
actual computation.

The tool is three lines: a function called calculate that hands an expression
to SymPy and returns the exact result.

[SCREEN: screencast, the system prompt + loop cell, scroll through it slowly]

Now the loop, and this is the notebook 2 centerpiece.

The system prompt tells the model: you have one tool, calculate. If the
request needs it, respond with only this JSON, a tool name and arguments.
Otherwise answer normally. That prompt is the entire tool registration.
Remember, it's just text in the context.

We ask a question that needs math: if 4,823 stores each sell 3,917 units,
how many units in total?

[SCREEN: run the cell, point at each printed piece as it appears]

Run it and follow the five steps live. The model responds with the JSON, you
can see it printed, "Model said." Our code parses it with json.loads and
calls calculate with those arguments. Then we append two messages, the
model's request and the tool's result, and call the API again. And the final
answer comes back with the correct number in it, because the number came from
SymPy, not from the model's memory.

That's a tool loop. Everything agents do from here on is this pattern with
more tools and more rounds.

[6:30] WHAT CAN GO WRONG
[SCREEN: deck 04, slide 4 (failure points)]

Now, the version we built trusts the model completely, and that trust can be
broken in four standard ways.

The model can wrap the JSON in prose, and parsing dies on the first word. It
can invent a tool that doesn't exist, ask it about the weather and watch. It
can produce valid JSON with the wrong argument names. Or the arguments can
reach the function carrying something it was never written to handle.

Notice the shape all four share: the failure happens at the boundary where
the model's output meets your code. Checking and validating at that boundary
is what makes a tool loop reliable.

Notebook 2 ends with an exercise called Break it, where you cause these
failures on purpose, using nothing but the user message. I'd genuinely
recommend doing it. Discovering the failure modes yourself teaches more than
any list on a slide.

[7:40] IS IT FAST ENOUGH: THE THREE METRICS
[SCREEN: deck 05, slide 2 (the three metrics)]

The loop works. Notebook 3 asks the engineering question: is it usable? Two
checks, speed and cost.

Speed first. Three metrics, each answering a different question.

TTFT, time to first token: how long before anything appears. This is what
makes a model feel responsive, and it matters most in chat, where a long
silence reads as a failure.

Tokens per second: how fast the response is produced once it's started. It
matters most when someone is reading the output as it streams.

And end-to-end latency: total time, request to complete output. It matters
most when nothing streams, batch jobs, and, importantly for us, every
internal step of an agent. An agent that takes ten model calls per task
stacks up ten of these before the user sees anything.

[SCREEN: screencast, playground response with the metrics underneath]

You've already seen these numbers, by the way. They're the figures under
every playground response. When you call from code, latency is measured on
the client side, and notebook 3 shows how.

[9:00] IS IT CHEAP ENOUGH: THE COST CALCULATION
[SCREEN: deck 06, slide 2 (two token counts, two prices)]

Cost second, and you already have both halves of this.

From the model card: two prices, per million tokens, input and output. From

request is those multiplied together. One line of arithmetic.

[SCREEN: screencast, notebook 3 cost cell running, the printed cost]

In notebook 3 we run it on a live request. Input tokens, output tokens, and
the cost, a fraction of a cent. Which feels like nothing, until you remember
that production means thousands of requests, and agents make several calls
per task. The habit to build is knowing what every request costs, from day
one, while the numbers are still small.
